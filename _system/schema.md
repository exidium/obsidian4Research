# Note schema (v2, mirrors ADI Dovetail conventions)

Every research note has a `type` property. Queryable metadata lives in frontmatter only. **Fields describe the source** (who, how, when, state). **Tags classify what was said** in a highlight. Tags take the form `dimension/slug`; workspace dimensions are defined in `_system/taxonomy.yaml`, project tag groups in each project's `tags.yaml`.

## Project folder

```
10 Projects/YYYY_slug/
  01 project.md         Study Overview (required), three top-level sections: Study overview (introduction, research questions
                        and methodology, participants), Findings (reports, insights), Operations & data (links to 02 and 03)
  02 insights review.md hub: highlight review board (proposed / accepted / rejected), from _system/templates/insights-review.md
  03 tag board.md       generated by tag_board.py: tag board plus one Kanban of highlights per tag group
  a_setup/              SETUP docs you own: Research Brief, Discussion Guide; STIMULUS docs shown to participants
    boards/             tags.base, tag-board.base, tag-board.canvas: generated board structure (content is live); never hand-edit
  b_sources/            S-####.md, one per data entry (immutable transcript + block IDs)
    reference/          REFERENCE docs imported for context (PRD, SOW, competitive analysis) with Source + Last synced header
  c_highlights/         H-S####-#### <title>.md, one idea each, aliased by ID
  d_tags/
    tags.yaml           project tag groups (numbered), each tag with a definition and status
    <group>/<slug>.md   generated tag pages (type: tag; definition, counts, live highlight list); never hand-edit
  e_insights/           I-<project>-## <finding>.md, one theme each, evidence-linked
  f_deliverables/       the actual deliverable files: readouts, decks, journey maps (listed in 01 project → Reports)
  (the three numbered pages are the only files at the project root)
00 Synthesis/<domain>/  Landscape, What We Know, Open Questions, Study Index (one per product domain)
```

## 20 Participants/P-###.md and 30 Personas/PE-## <role> who <behaviour>.md

Vault-wide. The participant card is generated by `participants.py sync` from the Rally export (public half: role, seniority, experience band, market, industry, region, country, company size, tools, consent flags, retention date, projects, sources; `persona` is the only hand-set property and survives syncs). The identity half (`_raw/participants/P-### identity.md`: name, employer, email) is local only and embedded by the card.

A persona is titled by role and one defining behaviour in plain words (`PE-02 Field engineer who patches the tool's gaps for forty accounts`), never an archetype label or a first name. The note has `type: persona`, `persona_id: PE-##`, `name` (the title without the ID), `status` (proposed | draft | reviewed), `archetype`, `participant_type`, `markets`, `participants`, `projects`, `evidence_highlights`. Body: Who, Jobs to be done (When…, I want…, so I can…), Behaviours, Pain points, What earns their trust, How to research with them, and a generated **Where they appear** section (projects, sources, highlights, insights, from `personas.py refresh`). Every participant card points at exactly one persona.

## b_sources/S-####.md

```yaml
type: source
source_id: S-0001
project: 2026_demo-fluxbench
title: "[Interview] P-001 - 14 Oct 2026"   # [Type] P-### - DD Mon YYYY
entry_type: interview                  # interview | workshop | feedback | survey | test | observation | demo | diary
methodology: user-interview            # user-interview | usability-test | workshop | survey | guerilla-testing | demo | card-sorting | diary-study
participant: P-001
participant_type: external-customer    # external-customer | internal-stakeholder | internal-engineer
role: "hardware design engineer"
software_used: [software/ltspice]      # tools the participant USES (field), not tools they mentioned (tag)
interviewer: P-000
rally_id: "DEMO-C-001"                 # consent record in Rally; required for external participants
date: 2026-10-14
duration_min: 48
language: en
origin: _raw/2026_demo-fluxbench/P-001.mp4
transcriber: mlx-whisper/large-v3-turbo   # or teams | krisp | dovetail-export | manual
speakers_inferred: false
redacted: true
ris_status: raw                        # raw | in-progress | review | published | excluded | archived
```

Reading a transcript: the Strange New Worlds plugin badges each block that a highlight references; hover for the highlights, click to open. The transcript file itself carries no marks. Body: `## Summary` (five descriptive bullets) then `## Transcript`, one paragraph per speaker turn, each ending in a block ID `^s0001-0012`. Immutable after ingest. Researcher annotations do not go into the transcript; they go into the highlight's `context`.

## c_highlights/H-S####-#### <title>.md

The file name is the ID followed by a short title that passes the stranger test on a tag board ("Latency documentation gap", not "Highlight 6"). The ID is an alias for search only: link the file name with the ID as display text (`[[H-S0001-0003 Spreadsheet wins when tool and spreadsheet disagree|H-S0001-0003]]`), because a bare `[[H-S0001-0003]]` does not resolve in Obsidian.

```yaml
type: highlight
highlight_id: H-S0001-0003
aliases: [H-S0001-0003]
title: "Spreadsheet wins when tool and spreadsheet disagree"
project: 2026_demo-fluxbench
source: "[[S-0001]]"
block: s0001-0008
participant: P-001
quote: "verbatim, complete sentences, 1-2 minimum, never cut mid-thought"
context: "[CONTEXT: what prompted this, or the framing a stranger needs]"   # optional; also [Q:] [OBS:] [NOTE:]
tags: [insight/pain-point, sentiment/negative, journey/design, correlation/sim-vs-bench-gap]
review: proposed                       # proposed | accepted | rejected
created_by: ai                         # ai | human
model: claude-fable-5-1
skill_version: 0.2.0
created: 2026-11-06
```

Body: collapsed context callout (if any), the embedded block, and one `**Rationale:**` line (why this passage is significant and why these tags).

Tagging rules: at least one workspace tag; typically 2-3 across dimensions (insight + functionality + journey) plus project tags. Tag what is discussed, not who is talking. One highlight with several tags, never duplicates. Separate highlights for genuinely separate topics. Never highlight interviewer speech.

## e_insights/I-<project>-## <finding>.md

```yaml
type: insight
insight_id: I-2026_demo-fluxbench-01
aliases: [I-2026_demo-fluxbench-01]
title: "Insight: Engineers trust a result only after it matches the bench"
project: 2026_demo-fluxbench
status: draft                          # draft | reviewed | published
evidence_level: emerging               # strong = 4+ participants, emerging = 2-3, insufficient = 1 (don't write one yet)
participants: [P-001, P-003]
highlights: ["[[H-S0001-0003 Spreadsheet wins when tool and spreadsheet disagree|H-S0001-0003]]", "[[H-S0003-0008 Trust earned project by project|H-S0003-0008]]"]   # file name + ID as display text; bare IDs do not resolve
research_question: 1
tags: [insight/pain-point, correlation/sim-vs-bench-gap]
published_to: ""
created: 2026-11-06
```

Body sections, in order: Finding · Severity and impact · What this means · Evidence (embedded highlights) · Recommendations (decision-forcing) · Open questions. One highlight may serve several insights.

## d_tags/tags.yaml (project tags)

```yaml
project: 2026_demo-fluxbench
groups:
  - id: correlation
    name: "3. Simulation vs bench"
    tags:
      - id: correlation/sim-vs-bench-gap
        definition: Apply when the participant compares a simulated value to a measurement and reports a gap.
        status: active            # proposed | active | deprecated
        evidence: [H-S0003-0001]  # for proposed tags
        merged_into: ...          # for deprecated tags
```

Group ids must not reuse a workspace dimension name. AI may add `proposed` project tags with evidence; only the researcher activates them. Workspace tags are never changed here.

## Media: recordings, clips, reels

Media lives in `_raw/<project>/` and never in git; notes hold pointers. In production `_raw/<project>` is the OneDrive-synced SharePoint study folder. `media.py` (skill `research-clip`) writes these properties; don't hand-edit them.

```yaml
# source note, added by `media.py link` (frontmatter only; the transcript is untouched)
recording: _raw/2026_demo-fluxbench/S-0001.mp4
recording_url: "https://…sharepoint.com/…"     # optional: the file in the SharePoint study folder
recording_sha256: 5359426b…                    # `media.py check` compares the local file against this
recording_duration: 00:10:37
redact_regions: [{x: 658, y: 476, w: 318, h: 42, label: name-plate}]   # recording pixels, blurred in every clip

# highlight note, added by `media.py clip`
clip: _raw/2026_demo-fluxbench/clips/H-S0001-0006.mp4
clip_kind: video                               # video | text-card (internal participants: no voice or video)
clip_start: '00:04:57.6'
clip_end: '00:05:04.9'

# insight note, added by `media.py reel`
reel: _raw/2026_demo-fluxbench/reels/I-2026_demo-fluxbench-02.mp4
reel_duration: 00:01:09
```

The clip and reel are also embedded in the note body (`![[_raw/…mp4]]`), under the transcript block and under the insight heading. People without the media see a missing-file placeholder, which is the intended behaviour.
